# APIO

## Current Hardware Architecture

The current design is a small programmed instruction engine:

```text
instruction_in -> instruction_memory -> decoder -> control signals
																			^             |
																			|             v
															program_counter <- delay_counter
																										 |
																										 v
																									 start
```

`instruction_memory` is programmed sequentially while `write_enable` is high.
The program counter addresses the memory, and `decoder` translates the current
instruction into GPIO, jump, and delay controls. `program_counter` advances
only when the internal execution enable from `delay_counter` is asserted.

The external `start` input enables execution. It does not directly force the
PC to increment: the delay counter can temporarily suppress the internal
execution enable while an instruction delay is active. GPIO state changes use
the same execution enable, so a delayed instruction performs its GPIO action
once and does not repeat while waiting.

### Instruction Format

Every 32-bit instruction includes its delay value:

```text
31       28 27       24 23                         0
+-----------+-----------+----------------------------+
|   opcode  | delay[3:0]|          operand           |
+-----------+-----------+----------------------------+
```

The delay field is the number of additional clock cycles to hold before the
next instruction executes. For example:

```text
SET GPIO[0], delay 3   = 32'h2300_0001
CLEAR GPIO[0], delay 3 = 32'h3300_0001
```

Each instruction executes on one clock edge, followed by three suppressed
execution edges. Together, these two instructions generate a square wave with
eight clock cycles per full period, or `f_clk / 8`.

Supported opcodes are `JUMP` (`0001`), `SET_GPIO` (`0010`), and `CLEAR_GPIO`
(`0011`). Jump operands use the low 24 bits; GPIO instructions use the low
eight bits.

## ISR

Interrupt service routines are not implemented in the current RTL. There is no
interrupt input, interrupt vector, return-from-interrupt instruction, or
register state for saving the interrupted PC.

A future ISR implementation would need an interrupt request input, an enabled
interrupt state, a vector address, and a saved return PC. The control sequence
would be:

1. Finish the current instruction and stop normal PC execution.
2. Save `pc_out` into an interrupt-return register.
3. Load the ISR vector into the PC.
4. Execute the handler and return with a dedicated `IRET` instruction.
5. Restore the saved PC and resume the delay-counter-controlled instruction stream.

The delay counter should be drained or explicitly cancelled on interrupt entry
so an interrupted instruction cannot be executed twice.

## Tools

The synthesis workflows use:

- `Yosys` for RTL synthesis, checks, and netlist generation
- `ABC` through Yosys for gate mapping
- `xdot` for the hierarchical block diagram
- `netlistsvg` for conventional gate-symbol diagrams
- `Inkscape` for PDF export of gate diagrams
- `xdg-open` to open generated GUI files

Install the optional gate-diagram renderer with:

```sh
npm install -g netlistsvg
```

## Synthesis

The synthesis script uses `Yosys` to check the RTL, report the synthesized
logic, and write a synthesized Verilog netlist.

Run it with a top-module name or top-level Verilog file:

```sh
./synthesize.sh top_v1
./synthesize.sh top_v1.v
./synthesize.sh top_v1 --sch
```

Available modes:

| Command | Result |
| --- | --- |
| `./synthesize.sh top_v1` | Synthesis report and Verilog netlist |
| `./synthesize.sh top_v1 --gui` | Hierarchical module-block view |
| `./synthesize.sh top_v1 --sch` | Alias for `--gui` |
| `./synthesize.sh top_v1 --hier` | Hierarchical module-block view |
| `./synthesize.sh top_v1 --gates` | Flattened gate-symbol PDF/SVG view |

The report and generated files are written to `/tmp/apio/`:

```text
/tmp/apio/top_v1_synthesis.log
/tmp/apio/top_v1_synthesized.v
```

The synthesized file is ordinary Verilog containing registers, muxes, and
logic cells generated by Yosys. Open it in VS Code with:

```sh
code /tmp/apio/top_v1_synthesized.v
```

Or inspect it in the terminal:

```sh
sed -n '1,120p' /tmp/apio/top_v1_synthesized.v
```

To validate the generated netlist again:

```sh
yosys -p 'read_verilog -sv /tmp/apio/top_v1_synthesized.v; hierarchy -top top_v1; check; stat'
```

### Netlist GUI

Pass `--gui`, `--sch`, or `--hier` to synthesize and open the hierarchical
module-block schematic automatically:

```sh
./synthesize.sh top_v1 --gui
```

The hierarchical view preserves the module instances under `top_v1`, such as
`decoder_i`, `instruction_memory_i`, `program_counter_i`, and `gpio_i`. It is
opened with `xdot`, and the DOT file is saved at:

```text
/tmp/apio/top_v1_hierarchy.dot
```

The viewer supports zooming and panning. It does not provide Vivado-style
click-to-expand inside one canvas; inspect a child module with a focused Yosys
command.

### Open Child Modules

To inspect a child module, select that module as the Yosys top and generate a
focused diagram. For example, to view `decoder`:

```sh
yosys -p 'read_verilog -sv src/decoder_v1.v; hierarchy -top decoder; proc; opt; check; show -format dot -prefix /tmp/apio/decoder decoder'
xdot /tmp/apio/decoder.dot
```

Other child-module commands:

```sh
yosys -p 'read_verilog -sv src/inst_mem.v; hierarchy -top instruction_memory; proc; opt; check; show -format dot -prefix /tmp/apio/instruction_memory instruction_memory'
xdot /tmp/apio/instruction_memory.dot

yosys -p 'read_verilog -sv src/prog_counter.v; hierarchy -top program_counter; proc; opt; check; show -format dot -prefix /tmp/apio/program_counter program_counter'
xdot /tmp/apio/program_counter.dot

yosys -p 'read_verilog -sv src/gpio.v; hierarchy -top aio_gpio; proc; opt; check; show -format dot -prefix /tmp/apio/aio_gpio aio_gpio'
xdot /tmp/apio/aio_gpio.dot
```

The focused diagrams are saved in `/tmp/apio/`.

For the flattened conventional gate-symbol schematic, use `--gates`:

```sh
./synthesize.sh top_v1 --gates
```

This uses Yosys, ABC, `netlistsvg`, and Inkscape to generate a vector PDF.
Install `netlistsvg` with:

```sh
npm install -g netlistsvg
```

Inkscape is also required for PDF output. The gate view is flattened by
design; use the hierarchical mode when module boundaries matter.

The PDF, SVG, and JSON files are saved at:

```text
/tmp/apio/top_v1_netlist.pdf
/tmp/apio/top_v1_netlist.svg
/tmp/apio/top_v1_netlist.json
```

The visualization copy treats bidirectional GPIO pins as inputs because the
installed netlistsvg schema does not support `inout` ports. This affects only
the diagram; the RTL and synthesized Verilog retain the correct bidirectional
GPIO connections.

To open the gate schematic SVG directly in VS Code:

```sh
code /tmp/apio/top_v1_netlist.svg
```
